### Production object inventory

- All 7 application tables have RLS enabled; FORCE RLS is false.
- No views or materialized views were found in `public` or `private`.
- The inspected production functions include `mobflow_save_state`, `accept_receiving`, `finalize_receiving_decisions`, `private.current_account_id`, `private.current_account_role`, `enforce_mobflow_account_allowlist`, and `rls_auto_enable`.
- Four application RLS policies were returned: three on `app_state` (SELECT/INSERT/UPDATE, tenant-scoped) and one SELECT policy on `profiles`.
- The application indexes and constraints were enumerated from the live catalogs. The key FKs for profiles, app_state, companies, and recovery tokens point to `auth.users`.
- One application trigger was found on `auth.users`: `mobflow_account_allowlist` (BEFORE INSERT).
- A production event trigger `ensure_rls` enables RLS on newly created public tables. Supabase-managed event triggers also exist and must not be copied blindly.
- Extensions observed: `pg_stat_statements`, `pgcrypto`, `plpgsql`, `supabase_vault`, `uuid-ossp`.
- Private Storage bucket `mobflow-payment-proofs`: 5 MiB limit; JPEG, PNG, WebP, PDF; no storage.objects RLS policies were returned.

### Security observation

The production grants include broad privileges for `anon` and `authenticated` on at least `app_state` and `profiles`, including TRUNCATE. RLS does not protect TRUNCATE. Do not reproduce those grants in Neon. Destination privileges must be minimal and paired with server-side tenant authorization.

## Critical design gate before DDL

The source schema is tightly coupled to Supabase Auth:
- `profiles.id` and `profiles.account_id` reference `auth.users`.
- `app_state.owner_id`, `companies.account_id`, `companies.payment_confirmed_by`, and `manager_password_recovery_tokens.account_id` also reference `auth.users`.
- SQL functions call `auth.uid()`.

Therefore, the first Neon schema must not be generated by mechanically copying these FKs/functions. The migration must first choose and document a temporary identity bridge that keeps the existing Supabase Auth provider while the database is tested, without enabling Neon Auth or changing production login. The bridge must be test-only, server-verified, and must preserve the exact user UUID/account UUID semantics. No client-supplied account ID may be trusted.
