## TanStack route integration

The repository uses file-based TanStack Start routing. The route README explicitly says routeTree.gen.ts is generated and must not be edited manually.

The official TanStack Start server-route pattern is createFileRoute(path) with server.handlers.GET/POST. The custom src/server.ts delegates requests to the TanStack Start server entry, so the new API routes can be added without replacing the existing SSR error wrapper or CSRF middleware.

## Driver decision

Use the official @neondatabase/serverless driver, version 1.2.0, on the Vercel Node runtime. It supports Node 19+ and provides Pool/Client APIs compatible with transaction-oriented server code. Use the pooled Neon connection endpoint and a very small per-instance pool. Keep the connection string exclusively in server environment variables.

This driver avoids adding the larger node-postgres dependency tree. The package has no runtime dependencies in the published 1.2.0 metadata.

## Authentication and transaction boundary

- The browser continues to use the existing Supabase Auth session.
- The server validates the bearer token by calling Supabase Auth's user-verification endpoint; decoded JWT claims alone are not accepted.
- The verified Supabase user UUID is the only trusted identity input.
- In one Neon transaction: set transaction-local app.user_id, read profiles by verified UUID, reject missing/inactive profiles, derive account_id/role/permissions from that row, then set transaction-local app.account_id and app.role.
- All tenant-scoped state reads/writes run on the same transaction/client.
- No session-level SET, no client-supplied tenant authority, and no browser database connection.
